# 동시성 / 데이터 정합성 문제 해결 정리

선착순 한정수량 쿠폰 발급 API와 게시글 조회수 증가 API에서 발생하는 동시성 문제를
직접 재현하고, 여러 해결책을 브랜치로 구현·측정해 비교한 뒤 선택한 기록.

> **측정 조건**: 로컬 단일 JVM, 스레드 풀 50, PostgreSQL 16 / Redis 7 (Docker).
> 절대 성능이 아니라 방식 간 **상대 비교값**이며, 각 수치는 3회 실행 범위로 표기.
> 재현/검증은 `ExecutorService` + `CountDownLatch` start gate 로 N개 스레드를 동시에
> 임계구역에 진입시키는 테스트(`*ConcurrencyTest`)로 수행.

## 1. 쿠폰 발급 — 초과 발급 & 중복 발급

### 문제

| 시나리오 | 기대 | naive 결과 |
|---|---|---|
| 서로 다른 유저 300명 동시 발급 (재고 100) | 100건 발급 + 200건 거부 | **300건 전부 발급 (+200% 초과), 거부 0건**, 재고 카운터는 34 |
| 같은 유저 100회 동시 요청 | 1건 | **9~10건** |

- **초과 발급**: `쿠폰 조회 → 재고 검사 → 재고 +1 & 발급 기록` 이 원자적이지 않음(check-then-act).
  여러 트랜잭션이 같은 재고 값(예: 99)을 읽고 모두 검사를 통과해 버린다.
- **카운터 유실**: `issued_count += 1` 이 read-modify-write. READ COMMITTED 에서 동시
  트랜잭션이 서로의 미커밋 증가를 못 봐, 300건이 발급됐는데 카운터는 34에서 멈춘다(lost update).
- **중복 발급**: 애플리케이션 `existsByCouponIdAndUserId` 검사만으로 방어. 동시 요청이
  이 검사를 함께 통과해 같은 유저에게 여러 장이 나간다.

### 해결

1. **중복 발급 → DB 유니크 제약** `(coupon_id, user_id)` + `saveAndFlush` 로 제약 위반을
   서비스 계층에서 포착. `existsBy` 는 1차 방어(빠른 실패)로 유지, 정합성 최종 보장은 DB.

2. **초과 발급 → 4가지 방식을 브랜치로 구현·측정**

| 방식 | 브랜치 | 결과 | 300건 처리시간 (3회) |
|---|---|---|---|
| naive | — | 300건 발급, 거부 0 | 0.52 – 0.65s |
| 낙관적 락 (`@Version` + 재시도) | `solution/optimistic-lock` | 100/100 | **1.16 – 1.25s** |
| 비관적 락 (`SELECT … FOR UPDATE`) | `solution/pessimistic-lock` | 100/100 | 0.72 – 0.89s |
| 조건부 원자 UPDATE (`… WHERE issued_count < total`) | `solution/atomic-update` | 100/100 | 0.49 – 0.58s |
| Redis Lua | `solution/redis-lua` (→ main 병합) | 100/100 | 0.37 – 0.65s |

3. **최종 채택: Redis Lua** — `중복 검사(SISMEMBER) → 재고 차감(GET/DECR) → 발급 기록(SADD)`
   을 Lua 스크립트 하나로 원자 실행. Redis 단일 스레드 + 스크립트 원자성이라 락도 재시도도
   없이 check-and-decrement 성립. DB 는 사본으로 뒤따라 기록 + 유니크 제약을 최종 방어선으로 유지.

### 성과

- **초과 발급 +200% → 0%** : 300 동시 요청 → 정확히 100건 발급, 200건 정상 거부.
- **중복 발급 유저당 9~10건 → 1건**.
- **카운터 유실 제거** : 발급 이력 수 = 재고 카운터 = 100 으로 일치.
- **300 동시 요청 처리 시간 : 낙관적 락 대비 약 2~3배 단축** (1.2s대 → 0.4s대), 재시도 폭증 없음.
- 부하 테스트(k6): **~7,600 req/s** 에서 9만 건 요청 → 초과 0 (issued=100, 이력=100).

## 2. 게시글 조회수 — 카운트 유실

### 문제

| 시나리오 | 기대 | naive 결과 |
|---|---|---|
| 1000회 동시 조회 | 1000 | **약 110 (≈ 89% 유실)**, 예외 0건 |

- `조회수 읽기 → +1 → 저장` 의 read-modify-write. 동시 트랜잭션이 같은 값을 읽고 같은 값을
  써서 증가분이 사라진다. 예외 없이 조용히 유실되는 것이 특징.

### 해결

| 방식 | 브랜치 | 결과 | 처리시간 (3회) | 조회 1000건당 DB 쓰기 |
|---|---|---|---|---|
| naive | — | ~110 / 1000 | 1.5 – 1.6s | 1000회 |
| DB 조건부 원자 UPDATE | `solution/article-db-atomic` | 1000 / 1000 | 1.4 – 1.6s | 1000회 |
| **Redis write-back** (채택, `main`) | `main` | 1000 / 1000 | **0.5 – 0.53s** | **1회 (flush당)** |

- 조회 시 `INCR article:view:delta:{id}`(원자적, O(1)) + dirty set 등록. DB 는 안 건드림.
- `@Scheduled`(기본 2초) + Redisson 분산락으로 **한 인스턴스만** 주기적으로 flush:
  dirty set 순회 → `SREM` **먼저** → `GETDEL delta` → `UPDATE … view_count = view_count + delta`.
- `SREM` 을 먼저 하므로 flush 도중 들어온 조회도 다시 dirty 로 등록되어 유실 없음.

### 성과

- **조회수 유실 89% → 0%**.
- **DB 쓰기 : 조회 1000건당 1000회 → flush당 1회 (약 99.9% 감소)**.
- **1000 동시 조회 버스트 처리 시간 : 약 1.5s → 0.5s (약 3배 단축)**. 부하 테스트(k6) ~8,300 req/s, p95 25ms.
- 트레이드오프: 조회수가 flush 주기(수 초)만큼 지연되는 **최종 일관성**을 수용하고,
  그 대가로 조회 트래픽에 비례하던 DB 쓰기 부하를 상수로 낮췄다.

## 3. Redis 장애 대비 (fail-safe + 복구)

Redis 를 발급 판정의 진실로 쓰므로 "Redis 가 죽으면?" 에 답할 수 있어야 한다.
장애를 실제로 주입해(`scripts/redis-failure-drill.sh`, 테스트 `CouponRedisRecoveryTest`) 확인.

| 장애 | 동작 | 정합성 |
|---|---|---|
| **연결 실패** (`docker stop redis`) | 발급 요청 → **503** (약 2초 내). Lettuce/Redisson timeout 을 2s 로 낮춰 매달리지 않음 | 발급이 안 됐을 뿐 DB 이력 불변 |
| **데이터 유실** (`FLUSHALL` — 재기동+AOF 갭 / eviction / 빈 복제본 failover) | Lua 가 `-2`(쿠폰 없음) 반환 → 발급 **404 거부** (fail-safe: 초과·유령 발급 안 생김) | DB 이력 불변 |

**복구**: `POST /api/coupons/{id}/redis-rebuild` — DB 의 `coupon_issue` 이력으로 Redis 재구축.
```
coupon:issued:{id} = coupon_issue 의 user_id 전체
coupon:stock:{id}  = total_quantity - 발급 이력 수
```
발급집합을 먼저 채우고 재고를 마지막에 SET (그 반대면 "재고는 보이는데 발급집합이 빈" 창에서
Lua 중복검사가 잠깐 뚫림 — 그래도 DB 유니크 제약이 막지만 창을 줄임).

→ **이것이 "Redis 가 hot path 권한을 가져도 DB 에 발급 이력 전체를 계속 남기는" 이유.**
DB = 내구성 있는 복구의 원천, Redis = 빠른 판정용 파생 상태.

## 4. 브랜치 맵

| 브랜치 | 내용 |
|---|---|
| `main` | 쿠폰 = Redis Lua + 장애 복구, 조회수 = Redis write-back |
| `solution/pessimistic-lock` | 쿠폰 초과 발급 = `SELECT … FOR UPDATE` |
| `solution/optimistic-lock` | 쿠폰 초과 발급 = `@Version` + 트랜잭션 밖 재시도 |
| `solution/atomic-update` | 쿠폰 초과 발급 = 조건부 원자 UPDATE |
| `solution/redis-redisson-lock` | 쿠폰 발급 = Redisson 분산락 |
| `solution/redis-lua` | 쿠폰 발급 = Redis Lua (main 에 병합됨) |
| `solution/article-db-atomic` | 조회수 = DB 원자 UPDATE (Redis write-back 이전 방식) |

## 5. 면접용 설명 — 판단 과정

### 접근 순서: "먼저 눈으로 보고, 싼 것부터"

1. **문제를 재현부터 한다.** 일부러 정합성이 깨지는 naive 버전 + 동시 요청 테스트로
   "300개 요청에 300개 발급, 아무도 에러를 안 받는다"를 먼저 눈으로 확인. 단일 스레드로는
   절대 안 터지므로, 동시 요청 재현 없이는 문제 자체가 안 보인다.
2. **가장 저렴한 해결책부터.** 중복 발급은 DB 유니크 제약 한 줄로 끝. 애플리케이션 검사는
   1차 방어로 남기되 **정합성 보장은 DB 에 맡긴다** — "정합성은 DB 가, UX 는 애플리케이션이".
3. **정답이 하나가 아닌 부분은 다 만들어보고 비교.** 초과 발급은 락/버전/원자연산/Redis
   네 가지를 브랜치로 구현하고 같은 재현 테스트로 정합성 + 처리 시간을 측정.

### 각 방식 한 줄 요약

- **비관적 락** — 쿠폰 행을 잠그고 순서대로. 확실하지만 완전 직렬화 + 락 구간에 INSERT 까지
  들어가 커넥션을 오래 잡음.
- **낙관적 락** — 안 잠그고 커밋 시 version CAS 만. 선착순 = 같은 행에 수백 명 → 충돌·재시도
  폭증. 실측 2~3배 느림. "충돌이 예외적일 때 쓰는 기법을 충돌이 일상인 곳에 쓰면 안 된다."
- **조건부 원자 UPDATE** — `재고 있으면 -1` 을 SQL 한 줄로. 락 구간 최소, 재시도 없음.
  **단일 DB 로 감당되면 1순위.**
- **Redis Lua** — 판정 자체를 Redis(싱글 스레드 + 스크립트 원자성)로. DB 가 병목일 만큼
  트래픽이 크거나 앱 인스턴스가 여러 대일 때. 대신 최종 일관성 + 운영 대상이 하나 늚.

### "왜 최종적으로 Redis 인가"

- 이 프로젝트가 상정한 시나리오는 **선착순 이벤트처럼 순간 트래픽이 DB 한계를 넘는 상황**.
  그때는 DB 락이든 원자 UPDATE 든 결국 DB 자체가 병목.
- 발급 판정을 Redis 로 올리면 DB 는 뒤에서 따라 기록만. 발급 경로에서 DB 를 뺄 수 있다(비동기화 여지).
- 안전장치: Redis–DB 불일치 대비 보상 + DB 유니크 제약(최종 방어선) + 장애 시 rebuild.
- **단일 DB 로 충분한 규모면 Redis 까지 안 간다** → `solution/atomic-update` 를 "작은 규모의 정답"으로 보존.

### "쿠폰과 조회수를 왜 다르게 풀었나"

- 정합성 요구 수준이 다르다. 쿠폰은 초과 = 사고 → 강한 정합성. 조회수는 몇 초 늦어도 무방 → 최종 일관성.
- 쿠폰은 Redis 로 **원자적 판정**, 조회수는 Redis 에 쌓아 **쓰기 부하 분산**(write-back). 같은 Redis 지만 목적이 다르다.

### 구현하며 마주친 함정

- **트랜잭션 경계 vs 락 경계** — 분산락에서 `unlock` 을 커밋보다 먼저 하면 커밋 전 상태를
  다른 노드가 읽는 창이 생김. 발급 로직을 별도 빈으로 분리해 "락 → (커밋 완료) → unlock" 강제.
- **`saveAndFlush`** — 유니크 제약 위반을 `try/catch` 로 잡으려면 즉시 flush 필요. `save` 만
  하면 예외가 커밋 시점(서비스 밖)에서 터져 못 잡음.
- **낙관적 락 재시도는 트랜잭션 밖에서** — 충돌 예외는 커밋 시점에 나므로 같은 트랜잭션에서 재시도 불가.
- **flush 중 유실 방지** — 조회수 flush 에서 `SREM` 을 `GETDEL` 보다 먼저.
- **Redis 장애 시 매달림** — Lettuce 기본 command timeout 60s. 2s 로 낮춰 빠르게 503 으로 실패.
- **macOS bash 3.2** — `$(...)` 안에 `\"` 를 중첩하면 파싱이 깨져 요청이 두 번 나감. 드릴
  스크립트는 JSON 을 `printf` 로 만들어 회피.
